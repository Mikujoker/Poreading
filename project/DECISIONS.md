# 关键决策

## D1：基于 `legado-with-MD3` fork，而不是从零写

**背景**：用户最初想「写一个全方位崭新的软件」。

**理由**：
- 书源引擎是重资产。书源规则是一门 DSL，含 `@css/@XPath/@json/@js`、`&&`/`||`/`##` 组合、
  `{{}}` 模板，其中 `@js:` 能调 `java.*`（AES/Base64/时间/正则…）。这些桥接层重写 ≈ 重写核心。
- 用户积累了 24528 条书源 + 281 本本地书 + 阅读进度。兼容性一旦掉到 80%，资产就废一半。
- MD3 分支本身已经做了大量工作：MD3 全量重构、predictive back、共享元素动画、阅读菜单重写、
  字体/字重/字距/排版设置、自定义 app 字体。

**取舍**：换掉「UI 层 + 排版层」，保留「书源引擎 + 数据层」。用户看到的每个像素都会换。

## D2：在原版之外共存安装

- 该分支 `applicationId = "io.legato.kazusa"`，与官方 `io.legado.app.release` 不同 → 并存
- 好处：原版一动不动，用户最怕的「更新把书弄没」根本不会发生
- 代价：数据要备份迁移一次（已完成）

## D3：在 WSL 里编译

- C 盘只剩 21 GB（且 WSL 发行版 vhdx 已在 `D:\WSL\Ubuntu`，不占 C）
- WSL 有 182 GB、20 核；Linux ext4 也避开 Windows 长路径坑（之前 `git clean` 就踩过）
- 实测：冷构建 11 分钟，增量 30~60 秒

## D4：本地书 bookUrl 用裸路径，而不是 SAF URI

**为什么必须改**：SAF `content://` 授权**绑定 app**，无法跨 app 转移；
而 `MANAGE_EXTERNAL_STORAGE` 只给裸路径权限。恢复备份后新 app 读不了任何本地书。

**方案**：把 bookUrl 从
`content://com.android.externalstorage.documents/tree/primary%3ADownload…`
改成 `/storage/emulated/0/Download/…`。

**为什么可行**：`LocalBook` 所有读写点都是
`if (uri.isContentScheme()) {…} else { File(uri.path!!) }` —— 裸路径是一等公民。

**实测验证**：`refreshToc` 返回完整目录、`getBookContent` 返回真实正文；
批量 281 本零失败，进度/书名/封面全部保留，**不需要删书重导**。

## D5：重复文件用「隔离」而不是「删除」

移到 `/sdcard/legado-trash/`（Download 之外，避免被目录扫描捡回来）。
确认无误后用户再删，可回收 182 MB。

## D6：先出 HTML 高保真原型，再改 Compose

改 Android 布局每版要编译 30~60 秒；HTML 原型在浏览器里 10 分钟能迭代一版。
定稿后再落代码。

## D7：书源筛选由 agent 在电脑侧做，手机 UI 只做「看结果 + 单条深操作」

**背景**：原本设计成五级状态 + 批量操作（冻结/启用/删除），让用户在手机上做批量分诊。

**用户反馈**：「我自己筛选特别蠢」「应该是你来帮我筛选」「全部改成一个待选书源清单，
只留常用和失效就行」。

**判断**：这是对的。批量分诊交给人在手机上做，既慢又做不好；而 agent 有全量数据、
能反复重跑、能做跨书源比较（比如「同域名同类型只留一条」—— 这在手机 UI 里根本做不了）。
所以职责切分改为：

- **agent（电脑侧）**：去重、挑出「能用的那条」、产出可导入的结果
- **手机 UI**：**三块 —— 常用 / 失效 / 全部** + 单条 AI 修复（用户明确指定，五级与批量操作全废弃）

**代价**：已经写好的五级分类与统计条要收敛成两级。数据层（SourceHealth 的判定逻辑）
可以复用 —— 只是把五个桶合并成两个，并把 UI 从「批量」改成「清单」。

## D8：不预计算健康度，改成「按需扫描 + 手动刷新」

**背景**：原设计预计算全部 24528 条的五级健康度，导致每次打开书源管理都要全表扫 119 MB（实测 2.6~5.9s，手机更慢）。
先试过落盘缓存（stale-while-revalidate），实测**仍有明显等待**。

**用户决定**：「改了吧，一会儿用不上缓存了，只需要在 **常用/失效/全部** 里的**失效**那块加一个**刷新**把失效选出来就行」。

**判断**：对。预计算的前提是「每次都要看全量统计」，但用户的真实需求只是
「把失效的挑出来」。按需扫描把成本从「每次打开都付」变成「点刷新才付」，这才是对的取舍。

**落地**：
- 删掉 `SourceHealthCache`（连同 ViewModel 的落盘接线）
- 三标签：常用 / 失效 / 全部；「失效」tab 带一个刷新动作触发扫描
- 复用 app 现成的书源校验；扫描结果缓存到内存即可（一次会话内有效）
- 预计算的统计条（5 格计数）废弃

## D9：常用是独立一列（≈收藏），与「启用」无关；失效 ⊆ 常用

**背景**：D8 之后我先把「常用」理解成「启用中的那些」，用户纠正：

> 「不是，启用是启用，常用是常用，常用和收藏差不多」「我没有选中成为常用的就不会测试失效」

**决定**：
- `book_sources` 新增 `isFavorite` 列（DB 107→108，迁移里同时重建 `book_sources_part` 视图），
  行上星标切换。**不复用「启用」，也不复用「分组」标签** —— 它是自己的一栏
- 三个标签：常用 = 打过星标的；失效 = 常用里校验判失败的（**失效永远是常用的子集**）；
  全部 = 全部
- 「失效」页的刷新**只校验常用**：没打成常用的源永远不测失效
- 推论：取消星标即退出失效列表（已装机验证）

**代价**：动库 + 一次迁移。收益是语义干净，且 `isFavorite` 跟着备份 / JSON 导出 / Web API 一起走。
