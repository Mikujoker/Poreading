## 一、动效标准（Emil，原样数值）

### 1. 先问「该不该动」

| 频率 | 决策 |
|---|---|
| 每天 100+ 次（键盘快捷键、命令面板开关） | **完全不动画。** |
| 每天几十次（悬停、列表内移动） | 取消或大幅削减 |
| 偶尔（弹窗、抽屉、toast） | 标准动画 |
| 罕见/首次（引导、庆祝） | 可以加惊喜 |

**键盘触发的动作永不加动画** —— 它一天要重复几百次，动画会让人觉得慢。
「看起来酷」对高频元素**不是**正当理由。正当理由只有：空间连续、状态提示、解释、反馈、避免突变。

### 2. 缓动

| 场景 | 曲线 |
|---|---|
| 进入 / 退出 | `ease-out`（先快，感觉响应快） |
| 屏幕上移动 / 形变 | `ease-in-out` |
| 悬停 / 颜色变化 | `ease` |
| 匀速（跑马灯、进度） | `linear` |
| 默认 | `ease-out` |

**UI 里永远不要用 `ease-in`** —— 它开头慢，正好拖住用户正在看的那一刻。

**CSS 内置曲线都太弱，要用强自定义曲线**：
```css
--ease-out:    cubic-bezier(0.23, 1, 0.32, 1);      /* UI 强 ease-out */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);      /* 屏内移动 */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);       /* iOS 抽屉曲线 */
```

### 3. 时长

| 元素 | 时长 |
|---|---|
| 按钮按下反馈 | 100–160ms |
| 提示、小浮层 | 125–200ms |
| 下拉、选择器 | 150–250ms |
| 弹窗、抽屉 | 200–500ms |

> **铁律：UI 动画保持在 300ms 以内。** 180ms 的下拉比 400ms 的更有响应感。

### 4. 物理感

- **永远不要 `scale(0)`**，从 `scale(0.9~0.97)` + `opacity:0` 开始。现实中没有东西是从"无"里出现的。
- **浮层从触发点长出来**（`transform-origin` 指向按钮），不是从中心。弹窗例外（居中）。
- **按钮按下反馈**：`:active { transform: scale(0.97) }` + `transition: transform 160ms ease-out`。

### 5. 错峰

- 多条入场错峰 **30–80ms**。再长就显得慢。
- 错峰是装饰性的，**绝不能阻塞交互**。

### 6. 无障碍

- `prefers-reduced-motion` 是**减少而不是归零**：保留 opacity/颜色，去掉位移。
- 悬停动效要用 `@media (hover: hover) and (pointer: fine)` 包住 —— 触屏上点按会误触发 hover。

### 7. 其它

- 同时改多个属性导致交叉淡入不干净时，过渡期间加 `filter: blur(2px)` 混合（不要超过 20px）。
- 只动 `transform` 和 `opacity`。
- 缓动要**和组件性格一致**：专业工具要"干脆快"，不要弹。

## 二、视觉工艺（Refactoring UI）

1. **少用边框。** 边框越多越乱。区分两个元素可以用：阴影、背景色差、或者干脆**留更多空间**。
2. **层级就是一切。**
   - 不要所有元素一视同仁
   - **尺寸不是唯一手段** —— 字重和颜色更细腻
   - **先做灰度**，别一开始就上颜色；灰度能站住，加了颜色才不乱
   - **去强调以强调**（弱化次要，主要自然凸显）
   - **标签是最后手段**（能靠位置/形态表达就别写标签）
   - 文字颜色**只用 2–3 档**
3. **别在彩色背景上用灰字。**
4. **一切都要有系统**：字号（几何级数）、字重、行高、颜色、间距（几何级数）、圆角、阴影、边框宽度。用到才定义，不要预先全铺。
5. 阴影要克制。

## 三、顶级个人站的取向（多篇复盘共识）

- 趋势是 **"少一点极简、多一点编辑感"**：更安静的配色、衬线排版、非对称布局、更多视觉材料。
- **真正的创造力不是套模板**：光标跟随、巨大字号、花哨特效只是"当下的审美"，不是设计。**每个动画都要服务于叙事，而不是装饰。**
- **信息密度 ≠ 杂乱**。杂乱是"没有层级的堆砌"。

## 四、对照审计：我们的原型违反了哪些

| # | 违规 | 我们现在的做法 | 应该改成 |
|---|---|---|---|
| 1 | **时长超标** | 列表入场 600ms、响应条 800ms、抽屉 500ms | 入场 **220ms**、响应条 **300ms**、抽屉 **280ms** |
| 2 | **错峰太密** | 24ms | **40ms**（落在 30–80 区间） |
| 3 | **`scale(0)` 类** | 对勾从 `scale(.2)` 起 | 从 **`scale(0.9)`** + opacity 起 |
| 4 | **`transition: all`** | 多处 | 逐条列出具体属性 |
| 5 | **边框过多** | 统计格 + 每行都加完整色边框 → 页面很吵 | 默认**色底 + 左侧色块**；边框只在**悬停/选中**时出现 |
| 6 | **hover 动效没 gate** | 直接写 `:hover` | 包 `@media (hover:hover) and (pointer:fine)` |
| 7 | **reduced-motion 归零** | `animation:none` | 保留 opacity，只去掉位移 |
| 8 | **字号不是级数** | 32/23/14.5/12/11.5/11 | 用几何级数 **34/22/15/13/11** |
| 9 | **文字颜色过多** | 3 档灰 + 5 个状态色同时用 | 文字**只用 2 档灰**；状态色只出现在色块/数字，不进正文 |
| 10 | **每行都挂标签** | 每行都显示 域名 · 分组 | 默认只留书名；**域名/分组移到悬停或选中时显示**（"标签是最后手段"） |
| 11 | 缺空/加载态 | 只有一行"无" | 补骨架屏与空状态 |

### 最重要的一条结论

**「动效看不出来」的根因不是幅度不够，恰恰相反 —— 是我把时长拉得太长了（600/800ms）。**
Emil 的标准是 UI 动画 ≤300ms。长动画不但显得拖沓，还会因为"慢"而让人感觉不到"动"。
正确方向是**更短、更干脆、错峰更均匀**，而不是更长更大。

同理「质感」：质感来自**层次、留白、材质（色底/阴影/模糊）**，不是来自加更多边框和更大动效。
**先灰度立住层次，再上颜色** —— 我们跳过了这一步，一开始就 5 个状态色 + 到处边框，所以显得杂。

## 六、落地检查表（改界面前过一遍）

### 动效
- [ ] 这个元素**每天出现 100 次以上**吗？是 → **完全不要动画**
- [ ] 「看起来酷」是不是我唯一的理由？是 → 删掉
- [ ] 进入/退出用 `ease-out`，屏内移动用 `ease-in-out`，悬停/变色用 `ease`
- [ ] **有没有用 `ease-in`？**（UI 里永远不要）
- [ ] 时长：按下反馈 100–160ms、浮层 125–200ms、下拉 150–250ms、抽屉 200–500ms，
      **一律 ≤300ms**
- [ ] 有没有从 `scale(0)` 开始？→ 改成 0.9~0.97 + opacity
- [ ] 可点元素有 `:active` 的 `scale(0.97)` 吗？
- [ ] 错峰在 30–80ms 之间吗？
- [ ] 悬停动效包了 `@media (hover: hover) and (pointer: fine)` 吗？
- [ ] 只动 `transform` / `opacity` 吗？有没有 `transition: all`？
- [ ] `prefers-reduced-motion` 是**减而不断**（保留透明度、去掉位移）吗？
- [ ] **有没有内容依赖动画才可见？**（`opacity:0` + 无 `forwards` 会让内容永远消失）

### 视觉
- [ ] 先做**灰度**能站住吗？颜色是不是在掩盖层级问题？
- [ ] 文字颜色是否**只用 2–3 档**？
- [ ] 边框是不是太多了？能用**背景色差 / 阴影 / 留白**代替吗？
- [ ] 是不是所有元素一样重？**去强调才能强调**
- [ ] 有没有在彩色背景上用灰字？
- [ ] 能靠位置/形态表达的地方，是不是还挂着**文字标签**？
- [ ] 字号是不是**几何级数**？还是随手定的 11.5 / 14.5？
- [ ] 圆角、间距、阴影是否来自同一套 token？

### 文案
- [ ] 有没有**句子**？（说明性副标题、解释性文案一律删）
- [ ] 有没有「A / B」并列短语、四字套话、自述式文案（AI 味）？
- [ ] 每一行文字删掉后，理解会受影响吗？不会 → 删
